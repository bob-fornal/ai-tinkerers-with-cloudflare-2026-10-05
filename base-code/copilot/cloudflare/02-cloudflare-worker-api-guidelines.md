# Cloudflare Worker API Guidelines

## Format & Syntax
* **ES Modules format:** Always use ES Modules syntax (`export default { fetch(request, env, ctx) { ... } }`) instead of the older Service Worker syntax (`addEventListener`).
* **Environment Variables & Bindings:** Access secrets and resources (like D1 bindings, KV namespaces) exclusively through the `env` object passed to the `fetch` handler.
* **Routing:** Use URL pattern matching with the `URL` API (`new URL(request.url).pathname`). A `switch`/`if-else` on the exact path is fine only for a handful of fully-static routes; the moment any route needs a path parameter (`/users/:id`), string-equality matching can't express it. Write a small (~50-line) segment-based matcher instead — split path and route into `/`-separated segments, treat a `:name` segment as a capture — rather than forcing parameters through string comparisons or reaching for an external router library. Register a static route before a parameterized route that could match the same segment count (`/users/me` before `/users/:id`) and match in registration order.
* **CORS:** Ensure endpoints handling cross-origin requests implement robust CORS headers, including handling preflight `OPTIONS` requests. Apply the same CORS headers to **every** response, including error responses (401/403/500) — an auth failure with no CORS header shows the browser a generic "CORS error" instead of the real status, which is much harder to debug from the client side. This includes routes with no auth requirement at all: "public" only means no token is required, not same-origin — a public endpoint called cross-origin by your own frontend (e.g. from a page that embeds no login) still needs the same explicit-allowlist CORS treatment as an authenticated one. Never reflect an arbitrary `Origin` header back — check it against an explicit allowlist of known origins.
* **Response Generation:** Always return standard web APIs `Response` objects (`new Response(...)`, `Response.json(...)`). Use proper status codes (e.g., 200 OK, 201 Created, 400 Bad Request, 404 Not Found, 500 Internal Server Error). Use one uniform error envelope shape across the whole API (e.g. `{ error: { code, message } }`) so every caller parses errors the same way regardless of which route failed.
* **Error Handling:** Wrap execution in `try/catch` blocks. Never expose internal stack traces or sensitive database errors directly in the unauthenticated API responses — `console.error`/`console.warn` the real error server-side (visible via `wrangler tail`) and return a generic message in the uniform error envelope. Catch a *specific* expected-conflict signal (e.g. SQLite's `UNIQUE constraint failed` message text) to distinguish an expected 409-worthy conflict from a genuine, loggable 500 — a blanket `catch` that turns every DB error into the same generic message hides real bugs behind expected-conflict noise.
* **TypeScript:** Prefer generating TypeScript code (`index.ts`) for Workers to leverage strict typing for the `env` bindings (using `interface Env { DB: D1Database }`). For a Workers AI binding (`env.AI`), don't reach for `@cloudflare/workers-types`' generated `Ai` interface if the model name is runtime-configurable (read from KV/D1, chosen by an admin) rather than a hardcoded literal — that generated type expects a literal model-name union per call. Declare your own narrower structural interface instead (`interface AiBinding { run(model: string, inputs: Record<string, unknown>): Promise<unknown> }`) so a `string` from configuration type-checks with no cast. Whatever the binding type, treat `env.AI.run()`'s result defensively — the typical shape is `{ response: "..." }`, but `response.response` is not guaranteed to be a `string` across models/runtime versions; normalize it (string passthrough, `""` for `null`/`undefined`, `JSON.stringify` otherwise) rather than calling `.trim()`/string methods on it directly.
* **Calling another Worker directly (Service Bindings + RPC):** when a capability deserves its own deploy lifecycle and its own, more narrowly-scoped credentials (e.g. a broader API token than anything else in the main app should hold), build it as a separate Worker whose default export extends `WorkerEntrypoint` (from `cloudflare:workers`), and bind it into the caller via `[[services]]` in `wrangler.toml`. The caller then calls its methods as plain async functions (`await env.MY_SERVICE.doThing(x)`) — no HTTP round trip, no `Response` to parse. The target Worker must already be deployed under the exact `service` name for calls to succeed; deploy order matters. This is real overkill for something that could just be a function import in the same Worker — reach for it when the isolation is the actual point, not as a default way to split code up.

## Performance & Security
* Validate all incoming request payloads before processing.
* Avoid blocking the event loop; make sure all external calls via `fetch()` and database queries are properly `await`ed.
* Use `ctx.waitUntil()` for background tasks like logging or analytics that don't need to block the response to the user.
